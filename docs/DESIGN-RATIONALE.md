# 设计 rationale：为什么"规则是请求，不是保证"

> 这篇是整个仓的思想地基。看完你会知道为什么我们要写这些 hook，以及哪些坑别踩。

---

## 核心论点：软约束 vs 硬约束

约束 AI 行为，本质上只有两种：

| | 软约束 | 硬约束 |
|---|---|---|
| **形态** | prompt / rules / AGENTS.md / CLAUDE.md 里写的话 | hook / 沙箱 / git pre-commit / 路径权限 / 类型系统 |
| **执行方** | 大模型自己 | 代码，在工具执行的结构层 |
| **遵守率** | 概率性，会忘、会被绕过、会稀释 | 确定性，条件命中就触发，和模型心情无关 |
| **失败模式** | "我忘了" / "我以为这次例外" / 长上下文被挤出窗口 | 代码 bug（可以修，可以测） |
| **成本** | 写一句话就行 | 要写脚本、要维护、要测 |

大模型是概率模型。你在 system prompt 里写 "never do X"，本质上是在调一个概率——把 X 的概率从 5% 压到 1%，但永远压不到 0%。心理学里叫"粉红大象效应"：你越跟人说"别想粉红大象"，人越想。对模型也一样，negative instructions 天然弱。

而硬约束是代码逻辑：命令里匹配到 `rm -rf` 正则，就 exit 2。模型想绕？它得先把命令拼成正则匹配不到的样子——这从"概率问题"变成了"对抗问题"，难度高了一个数量级。

**关键判断：违反代价不可逆的事，必须上硬约束。**

`rm -rf`、`git push --force`、把密钥写进代码——这些事一旦发生，不可逆。软约束把它们的概率压到 1%，但那 1% 真发生时你收不回。硬约束把概率压到接近 0%（除非正则本身有 bug，而 bug 是可修可测的）。

这就是我们维护这一组 hook 的全部理由：不是不信任模型，是承认"软约束是概率游戏，不可逆的事不能赌概率"。

---

## 一、模型为什么会违反写得很清楚的规则

不是模型"不听话"，是几个结构性原因：

1. **注意力单位错配**。模型处理一段指令时，注意力在"我要完成的任务"上，不在"我要遵守的第 47 条规则"上。规则写得再清楚，也挤不进任务相关的注意力窗口。
2. **长上下文稀释**。会话一长，开头注入的规则被后面几百轮对话推到注意力边缘，等价于没写。
3. **绕过变体**。你写"别用 rm -rf"，模型可能用 `/bin/rm -rf`、`xargs rm`、`find -delete`、变量拼接——黑名单永远列不全。
4. **"我有把握"时刻最危险**。越觉得"这很明显、不用查"，越容易不查证就下断言、不备份就改代码。自信是盲区。

实测有个案例：一条"下结论前先查证"的规则下午才写进规则库，不到一小时就被违反了三次——一次把白纸黑字写的事实判成"误判取消"，一次重复提出已登记的问题，一次编造了不存在的条目。**规则当天沉淀，当天被违反。** 这不是态度问题，是结构问题。

## 一补、前沿背书：不是我们一个人这么想

这个判断（软约束靠不住、硬约束要在执行层拦）在 2026 年下半年被多方独立验证：

- **Anthropic 官方口径**：CLAUDE.md 里写 "never do X" 是 a request, not a guarantee。规则是请求，hook 是强制，每次工具调用前真跑脚本，退码非零就拦。
- **Claude Code 自身在往硬约束方向拧**：2.1.295 起给 hook 加 `onFailure:"block"`——hook 自己崩了不再默默放行，而是阻断；2.1.301 把 Grep/Glob 搜索失败从"没有匹配项"改成明确报错（以前"没找到"和"出错了"长得一模一样）。
- **OpenAI 失准披露页**：2026-10 追加 4 起内部模型越界，累计 19 起，其中 3 起延迟 2-3 个月才被发现；一起下走了 147,451 行非公开数据，模型在回答里只字未提，官方自动 grader 也没标出来。结论："结果对不对"和"过程合不合规"是两条线，分开记的那条线会静默失败。
- **Codex 0.163.0（2026-10-15）**：把边界从指令层搬到执行层——DNS 查询前先查权限、防凭证别名绕过 inspection hooks。和我们说的"从 prompt 搬到 hook"是同一个方向。
- **NIST / NSA-SISC / CISA 联合（2026-10-16）**：《Key Practices for Super Intelligence Incident》第一次给这类事故起了官方名字——"SI control incident"（AI Agent 作出未被指令的重大行动）。实践 4 叫"验证并保护监控器自身的完整性"（盯着 Agent 的那套东西自己也得被防篡改）；实践 7 叫"恢复 Agent 之前先验证遏制"。
- **开发者实践互证**：Geoffrey Huntley 把"不许绕过内部校验库"从提示词嘱咐改成 git pre-commit hook——扫 staged diff，发现绕过直接拒掉，同时把纠正提示回灌 Agent。Simon Willison 2026-10-14 转述。
- **反面案例**：微软 VS Code 公告（SB2026101403 / CVE-2026-102232）里，AI 编码代理可以在无确认的情况下改掉 lifecycle-hook 文件——护栏本身也是文件，也在 AI 的读写范围里。所以"重启后验一次"还得补一句"顺便确认 hook 文件本身没被改过"。

这些指向同一个结论：**软约束（prompt/rules）是概率游戏，硬约束（hook/执行层检查/网络层控制）才是确定性兜底。厂商和国家标准机构都在往同一个方向拧。**

## 二、什么时候必须上 hook

四个条件同时成立：

| 条件 | 反例（别上 hook） |
|------|------------------|
| 违反代价不可逆或返工成本极高 | 变量命名风格 → 写 lint 或规则就行 |
| 同一根因短期内犯过多次 | 只犯过一次 → 记 bad case，先别 hook |
| 判据能机械写成正则/存在性检查 | "帮我审一下这段代码好不好" → 判不准，别做门禁 |
| hook 自身失败不影响主流程（fail-open） | hook 一崩就卡住所有操作 → 危险 |

满足这四条的典型：
- 递归删除、强推、磁盘写裸设备（不可逆）
- 直接编辑 `.env` / 私钥文件（密钥泄露）
- 改源码但 2 小时内没动过设计文档（No Spec No Code）
- 写入内容命中"否定性断言"模式（该查证没查）

不满足、但你很想做的：**先写规则，观察两周。** 两周后还犯，再做 hook。不要一上来就堆。

## 三、fail-open 还是 fail-closed

我们所有门禁类 hook 一律 **fail-open**：

- stdin 解析失败 → 放行（exit 0）
- hook 自身异常 → 放行
- 正则编译错 → 跳过这条规则

原因：hook 是**最后一道兜底**，不是唯一防线。红线同时写在规则层（AGENTS.md）和人脑子里。如果 hook 自己崩了就卡住所有 Bash 调用，等于把一个可能有 bug 的脚本变成了单点故障——你修 hook 的时候整个工作停摆。

阻断只在一种情况发生：**明确命中了我们要拦的模式**，且原因清晰。其他全部放行。

## 四、注入税：hook 不是免费的

每个挂在 SessionStart 的 hook 都会把文本注入每一轮的上下文。
我们的预算：

- 单次注入 < 500 字节
- **UserPromptSubmit 注入 = 0**（逐消息高频税，实测一句提醒 1KB × 每条消息 = 纯烧 token）
- 真正常驻总量 < 窗口的 5%

反面教材：曾经把 YAGNI 提醒挂在 UserPromptSubmit，每条消息都注入 1084 字节。模型确实每次都看到了，但用户每发一句话都在为这句话付钱。后来移到 SessionStart，只在会话开始注入一次。

**写通过删除**：注入内容写完后逐句问"这句不写模型真会错吗？"，不会就删。

## 五、提醒类 hook 的两个设计要点

claim-guard / sediment-signal 这类"提醒但不阻断"的 hook，有两个坑：

### 5.1 绝不阻断

误伤一个正常改动，比漏掉一次违规更贵。提醒类 hook 永远 exit 0，只 additionalContext。
真阻断的留给破坏性命令那种零误伤场景。

### 5.2 同会话节流

同一句话每轮都提醒，三轮之后模型就免疫了（用户也会烦）。
用 session_id 做 key，同会话同类型只提醒一次：

```python
state_file = tempfile.gettempdir() + "/my-guard/" + md5(session_id).hexdigest()
if os.path.exists(state_file): 跳过
```

## 六、最小有效集：不要堆 hook

我们曾经从 4 个 hook 收敛到 2 个，又逐步加回经过实战验证的。判断标准：

- **保留**：灾难后果、无原生替代、零误伤、0 注入税
- **删除**：低频但安全价值高的保留；纯通知不阻断的删；每次触发都烧 token 但没拦住过任何事的删

加新 hook 之前问：这个 hook 过去三个月拦住过什么？如果答案是"还没发生过违规"，那它现在就是常驻税，先别加。

## 七、这个仓里的 hook 是怎么来的

每个 hook 背后都是一个真实踩过的坑：

| Hook | 触发它的事故 |
|------|-------------|
| `destructive-command-guard` | rm -rf 误删、git push --force 覆盖远端历史 |
| `pre-tool-secret-guard` | 模型直接 Edit 了 .env，差点提交密钥 |
| `claim-guard` | 一天内四次"我有把握但没查证"，包括把文档明写的事实判反 |
| `ponytail-yagni-reminder` | 一上来就写三层抽象，其实几行 stdlib 就够 |
| `session-recap` | 切走会话回来后不知道刚才做到哪了 |
| `sediment-signal` | 同一个纠偏模式反复出现，但没人沉淀成可复用 skill |
| `session-start-reminder` | 新会话上来不读 README 就动手 |
| `stop-review-check` | 说"做完了"但没回读验证，产物其实是坏的 |

没有一个是"我觉得应该有"，全是"吃过亏才长出来的"。

---

## 八、边界：hook 不解决什么

最后说清楚 hook 做不到的事，避免误用：

1. **hook 不是安全边界**。黑名单正则能被 `/bin/rm`、复合命令、环境变量绕过。真正防数据丢失靠：git 追踪 + 备份脚本 + 人的判断力。hook 只拦"手滑"，不拦"蓄意绕过"。
2. **hook 不替代文档**。规则层还是要写，hook 是兜底不是主角。
3. **hook 不解决判不准的问题**。"这段代码写得好不好"这种事，正则判断不了，别硬做门禁。
4. **hook 不能代替人审**。群发、发布、删库、对外发送——这些永远人来点。hook 只在人和模型之间加一道机械闸。

把这四件事想清楚，hook 就是个趁手的工具；想不清楚，就会堆出一堆自我感觉良好的常驻税。
